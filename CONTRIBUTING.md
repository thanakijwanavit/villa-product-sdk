# How to contribute

## Repository layout

This is an [nbdev](https://nbdev1.fast.ai/) 1.x project. The notebooks are the source, and they sit at the **repository root** (`nbs_path = .` in `settings.ini`):

| Notebook | Generates |
|---|---|
| `index.ipynb` | `README.md` and the docs home page |
| `product-sdk.ipynb` | `villaProductSdk/products.py` |
| `Schema.ipynb` | `villaProductSdk/schema.py` |

The files in `villaProductSdk/` start with `AUTOGENERATED! DO NOT EDIT!`. Change the notebook, then regenerate. The generated HTML docs are in `docs/`.

## Getting started

Use Python 3.8 or 3.9 (see "Supported Python" in the README) and nbdev 1.x:

```bash
pip install "nbdev<2" pytest
pip install dataclasses-json boto3 requests lambdasdk s3bz ujson awsSchema "urllib3==1.25.10" nicHelper
nbdev_install_git_hooks
```

The second line installs the `requirements` listed in `settings.ini`. `pip install -e .` does not work yet: `setup.py` imports `pkg_resources`, which recent setuptools no longer ships (vps-3ug).

`nbdev_install_git_hooks` installs the hooks that strip notebook metadata on commit and avoid merge conflicts. Run it once after cloning.

## Making a change

1. Edit the notebook.
2. Run `nbdev_build_lib` to regenerate the Python modules.
3. Run `nbdev_build_docs` to regenerate `README.md` and `docs/`.
4. Run the offline tests with `python -m pytest tests`. They need no AWS credentials.
5. Commit the notebook and the regenerated files together.

Notebook cells that call the SDK reach live AWS. Run them only against the dev stage (`dev-manual`), with dev credentials from an AWS profile. Never paste keys into a notebook.

Known problem: `product-sdk.ipynb` and `villaProductSdk/products.py` have drifted apart. Running `nbdev_build_lib`, or the last cell of `index.ipynb`, rewrites `products.py` from the notebook. Check `git diff villaProductSdk/` before you commit.

## Reporting a bug

- Search the existing issues first.
- Include a title, a clear description, the complete error message, and a code sample or test that shows the problem.
- Do not report security problems in public: see "Security" in the README.

## Pull requests

- Keep each PR focused on one change, and include a test that fails without your patch.
- Do not mix style changes with functional changes.
- Describe the problem and the fix in the PR, and name the related issue.
